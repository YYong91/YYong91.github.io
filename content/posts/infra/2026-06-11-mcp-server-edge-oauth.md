## 📌 배경

Claude Code에서 우리 서비스(SynTitan)의 데이터셋을 바로 조회할 수 있게 만드는 작업을 했습니다. MCP(Model Context Protocol) 원격 서버를 구축하는 일이었는데, tool 하나(`list_datasets`)를 노출하는 것보다 **인증 아키텍처를 세우는 데** 작업의 8할이 들어갔습니다.

```bash
claude mcp add --transport http syntitan https://mcp.syntitan.ai/mcp
```

사용자가 보는 건 이 한 줄과 로그인 화면뿐이지만, 그 뒤에는 엣지 OAuth 서버, opaque 토큰, mTLS origin-lock이 있습니다. 이 글은 그 설계와 만들면서 밟은 함정 두 개의 기록입니다.

---

## 🏗 설계 원칙: 인증은 엣지에서 끝낸다

```
Claude Code ──(opaque 토큰)──▶ Cloudflare Worker (OAuth 서버 + 프록시)
                                  │  mTLS + IP 제한 (origin-lock)
                                  ▼
                              전용 ALB ──▶ 백엔드 (/mcp)
                                           "X-Auth-User-Id 헤더만 신뢰"
```

처음 정한 원칙은 하나였습니다. **백엔드는 MCP 인증의 존재를 몰라야 한다.**

OAuth 서버를 백엔드 안에 넣으면 토큰 발급·검증 트래픽이 전부 ECS로 들어오고 인증 코드와 비즈니스 코드가 섞입니다. 대신 Cloudflare Worker를 인가 서버로 세웠습니다. Cloudflare가 MCP용 OAuth 라이브러리(`@cloudflare/workers-oauth-provider`)를 공식 제공해서 동적 클라이언트 등록(DCR) 같은 스펙 구현 부담도 크게 줄었습니다.

결과적으로 백엔드가 하는 일은 헤더 한 줄을 읽는 것뿐입니다.

### 토큰 2층 구조

Claude Code가 받는 토큰은 Cognito 토큰이 아닙니다. Worker가 자체 발급한 **opaque 토큰**이고, 수명이 5분입니다.

| | JWT | opaque |
|---|---|---|
| 내용 | 디코드하면 보임 | 의미 없는 랜덤 문자열 |
| 검증 | 서명 확인 | 서버 저장소(KV) 조회 |
| 즉시 무효화 | 만료까지 어려움 | 저장소에서 지우면 즉시 |

opaque를 고른 이유는 **회수 가능성**입니다. 토큰↔권한 매핑이 Worker KV에 있으니, KV에서 grant를 지우면 그 자리에서 무효가 됩니다. Cognito 토큰(JWT)은 Worker 내부에만 머물고 외부로 나가지 않습니다.

수명 5분도 단점이 아니라 기능입니다. Claude는 refresh 토큰(30일)으로 자동 갱신하는데, **갱신할 때마다 Worker가 백엔드에 "이 사용자 아직 유효해?"를 물어봅니다.** 조직 관리자가 MCP를 끄거나, 사용자가 연결을 해제하거나, 계정이 비활성화되면 최대 5분 안에 차단됩니다. 영구 토큰을 뿌려놓고 회수 못 하는 문제가 구조적으로 없습니다.

### origin-lock: 헤더를 믿어도 되는 이유

백엔드는 요청자가 누군지 `X-Auth-User-Id` 헤더로만 압니다. "헤더를 신뢰한다"는 건 보통 위험한 설계입니다. 누군가 ALB를 직접 호출하면서 헤더를 위조하면 끝이니까요.

그래서 Worker→ALB 구간을 잠갔습니다.

1. **mTLS (1차)** — 전용 ALB의 :443 리스너가 클라이언트 인증서를 검증(`mutual_authentication mode=verify`)합니다. 인증서를 가진 Worker만 origin에 도달할 수 있습니다.
2. **공유 시크릿 (2차)** — Worker가 모든 요청에 `X-Edge-Secret`을 싣고 백엔드가 대조합니다. mTLS 설정 사고가 나도 이게 받칩니다.
3. **IP 제한 (3차)** — ALB 보안그룹이 Cloudflare 대역만 허용합니다. 단독으론 약한 방어(공유 대역이라 CF의 모든 고객이 통과 가능)라 보조로만 씁니다.

"Worker가 서명한 JWT를 전달하고 백엔드가 검증"하는 암호학적 대안도 검토했지만 기각했습니다. 그건 인증 로직(JWT 검증 미들웨어 + 키 회전)을 백엔드 안으로 다시 들여오는 것이기 때문입니다. mTLS는 같은 보장을 **앱 코드 0줄**로 네트워크 계층에서 제공합니다.

### 전용 ALB를 새로 만든 이유

기존에 웹소켓용 ALB가 있는데도 MCP 전용 ALB를 신설했습니다. 비용이 늘어나는 결정이라 근거가 필요했는데, 사실 선택지가 없었습니다.

- ALB의 mutual TLS는 **리스너 단위** 설정입니다. 기존 :443에 켜면 웹소켓으로 붙는 브라우저 전부가 클라이언트 인증서를 요구받고 죽습니다.
- 다른 포트 리스너를 추가해도 **보안그룹은 ALB 단위**입니다. "CF 대역만 허용(MCP)"과 "공개(웹소켓)"를 한 ALB에서 동시에 만족할 수 없습니다.

분리하니 "이 ALB로 들어오는 건 전부 Worker"라는 불변식이 단순해졌고, 기존 ALB는 한 줄도 건드리지 않아 운영 트래픽 회귀 리스크가 0이었습니다.

## 🔐 로그인 화면: SSO에 끼어들기

처음 버전은 Cognito가 기본 제공하는 로그인창(Hosted UI)을 그대로 띄웠습니다. 동작은 했지만 디자인 커스텀이 요금 티어에 막혀 있었고, 제품 통합 로그인과 완전히 따로 노는 화면이었습니다.

해법은 새 화면을 만드는 게 아니라 **기존 SSO에 Worker를 클라이언트로 편입**시키는 것이었습니다. 우리 제품들은 이미 통합 로그인 페이지의 `return_to` 규약(로그인 성공 → 암호화된 코드와 함께 호출자에게 리다이렉트)으로 SSO를 하고 있었습니다. Worker의 `/authorize`가 그 페이지로 보내고, `/callback`이 코드를 토큰으로 교환하도록 바꿨습니다.

- FE 로그인 화면 코드 변경: **0줄** (redirect 화이트리스트 env 한 줄 추가)
- 웹에 로그인된 사용자는 MCP 연결 시 **폼 없이 자동 통과**
- Cognito 직접 호출 코드는 Worker에서 전부 제거 — 토큰 교환·계정 재검증 모두 계정 서비스 API 경유

검증된 길에 올라탄 덕에 며칠 만에 끝났지만, 공짜는 아니었습니다. 두 번 제대로 넘어졌습니다.

## 🕳 함정 ①: 쿠키는 host 단위다

dev에서 첫 테스트를 돌리자 로그인 후 전부 `missing code/state` 에러로 죽었습니다.

CSRF 방어용 일회용 값(nonce)을 쿠키로 전달했는데, 쿠키는 host 단위로 저장됩니다. 사용자는 `mcp-dev.{도메인}`으로 진입했는데, 콜백 주소가 설정값에 `*.workers.dev`로 고정돼 있었습니다. **로그인을 마치고 다른 host로 돌아오니 쿠키가 따라오지 않았습니다.** 진입점 코드와 콜백 코드 각각은 멀쩡했고 "둘이 다른 host일 수 있다"는 조합만 놓쳤습니다.

수정은 콜백 URL을 고정값 대신 요청 host에서 동적으로 만드는 것이었습니다.

```ts
login.searchParams.set("return_to", `${url.origin}/callback`);
```

same-host가 항상 보장되니 쿠키가 무조건 왕복하고, 보너스로 prod 도메인도 코드 변경 없이 자동 대응됐습니다.

## 🕳 함정 ②: 우리 완료 화면에 머물 수 없는 이유

디자이너가 "연동 완료" 화면을 만들어줬으니, Claude가 띄우는 기본 "창을 닫아도 됩니다" 페이지 대신 우리 화면에서 플로우를 끝내고 싶었습니다.

계획은 그럴듯했습니다. 우리 완료 화면을 띄워두고, 인증 코드는 백그라운드 `fetch`로 Claude의 로컬 서버(`127.0.0.1`)에 전달한다.

배포하니 녹색 완료 화면은 떴는데 Claude가 인증 완료로 넘어가지 않았습니다. 콘솔에는 에러 한 줄 없었습니다.

원인은 Chrome의 **Private Network Access** 정책이었습니다. 공개 인터넷 사이트가 사용자 컴퓨터 내부(localhost)로 요청하는 것을 브라우저가 차단합니다. 악성 사이트가 로컬 장비를 공격하는 걸 막는 정책인데, 우리가 정확히 그 패턴이었습니다. 더 고약한 건 `no-cors` 요청이라 차단이 **무음 실패**로 처리된다는 점입니다. fetch는 성공한 것처럼 resolve되고, 그래서 폴백 로직마저 건너뛰었습니다.

조사해 보니 구조적 제약이었습니다. loopback 방식 OAuth(RFC 8252)에서 인증 코드 전달은 **페이지 이동(top-level navigation)으로만** 가능합니다. navigation은 PNA 적용을 받지 않지만, 이동하는 순간 우리 페이지를 떠나게 됩니다. gh, gcloud, aws CLI가 전부 자기(CLI) 페이지로 끝나는 이유가 이것이었습니다. 자기 브랜딩 페이지에 머무는 서비스들은 device code flow(폴링)를 쓰는 경우인데, Claude Code는 그 방식을 지원하지 않습니다.

결론: 우리 화면을 2.5초 보여주고 자동 이동하는 것으로 정리했습니다. "안 되는 게 맞다"를 확인하는 데 쓴 시간이었지만, 브라우저 보안 모델을 한 층 깊게 이해하게 된 디버깅이었습니다.

## 🚀 운영: 스위치 하나로 켜는 launch

배포까지의 운영 셋업 세 가지입니다.

- **시크릿 단일 원본** — Worker와 백엔드가 공유하는 시크릿을 Infisical 한 곳에 두고, AWS Parameter Store와 Cloudflare Worker 양쪽으로 자동 동기화합니다. 회전도 한 곳에서 합니다.
- **prod 배포는 태그로만** — 일반 push는 dev만 배포되고, prod는 `mcp-auth-prod-*` 태그를 밀 때만 나갑니다. GitHub free 플랜이라 Environment 승인 게이트를 못 쓰는 제약을 태그 트리거로 우회했습니다. 태그를 안 밀면 prod가 안 바뀌니, "까먹음"이 사고가 아니라 안전이 됩니다.
- **기능 플래그 launch** — prod 인프라(ALB, mTLS, Worker, DNS)를 전부 미리 올려두되 `MCP_ENABLED=off`로 잠가뒀습니다. launch 당일 할 일은 코드 배포와 스위치 on뿐입니다.

prod 인프라를 올리면서도 한 번 더 넘어졌는데, openssl이 기본으로 만드는 인증서는 **v1**이라 AWS ALB trust store가 거부합니다(`certificate version not supported`). CA는 v3 + `basicConstraints=critical,CA:TRUE`로 발급해야 합니다. 같은 명령으로 만든 dev 인증서는 우연히 통과 경로가 달랐던 게 아니라, dev 때는 v3 옵션을 넣고 prod 때 빠뜨린 것이었습니다. 회전 절차와 함께 README로 박제했습니다.

## 🏁 정리

| 결정 | 이유 |
|---|---|
| OAuth 서버를 엣지(Worker)에 | 백엔드에 인증 코드 0줄, 토큰 트래픽이 ECS에 안 들어옴 |
| opaque 토큰 5분 + 갱신마다 재검증 | 권한 회수가 최대 5분 안에 동작 |
| mTLS origin-lock | "헤더 신뢰"의 근거를 네트워크 계층에서 |
| 전용 ALB | mutual TLS가 리스너 단위 + SG가 ALB 단위라 분리 외 선택지 없음 |
| 기존 SSO에 클라이언트로 편입 | 로그인 화면 새로 안 만듦, FE 0줄 |
| 태그 기반 prod 배포 + 기능 플래그 | launch = 스위치 on |

MCP 서버 만들기의 본체는 tool 코드가 아니라 인증이었습니다. 그리고 인증의 본체는 토큰 발급이 아니라 **회수와 격리** — 토큰을 언제든 죽일 수 있는가, 인증이 뚫려도 비즈니스 계층이 격리돼 있는가 — 였습니다.
