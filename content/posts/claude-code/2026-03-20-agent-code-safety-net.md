## 📌 문제: 에이전트가 코드를 짜는 시대, 뭘 믿고 머지하나

Claude Code로 개발 속도가 빨라지면서 새로운 불안이 생겼습니다. 에이전트가 만든 코드를 내가 다 확인할 수 없다는 점입니다.

포도가계부(podo-budget) 프로젝트에서 코드리뷰를 돌렸더니 이슈가 75개 나왔습니다. 보안, 버그, 성능, 코드 품질 전방위입니다. 이걸 에이전트한테 시키려면, 에이전트가 코드를 고쳐도 안전하다는 확신이 필요했습니다.

결론부터 말하면: **에이전트 개발의 본질은 코드를 짜는 것이 아니라 안전장치를 설계하는 것**이었습니다.

---

## 🔄 에이전트 코드리뷰 루프

75개 이슈를 에이전트한테 넘기기 위해 설계한 패턴입니다.

```
이슈 이해 → TDD (실패 테스트 → 구현 → 통과) → 자기 코드리뷰 → 커밋
    → 그룹 완료 → 전체 테스트 + 최종 리뷰 → PR → CI → CD
        → 다음 그룹 자동 진행
```

### 핵심 원칙

**1. 이슈를 충분히 이해하고 나서 손대기**

`gh issue view`로 이슈 내용을 읽고, 관련 파일을 전부 읽은 다음에야 수정을 시작합니다. "대충 제목 보고 고치기" 금지입니다.

**2. TDD로 안전망 먼저**

"보수적"이란 최소한만 고친다는 의미가 아닙니다. 비효율적이면 구조적으로 개선해도 됩니다. 핵심은 **테스트를 먼저 확보**하는 것입니다. 실패 테스트를 먼저 작성하고, 구현하고, 통과를 확인합니다. 구조 변경으로 추가 테스트가 필요하면 그것도 TDD로 작성합니다.

**3. 자기 코드리뷰**

에이전트가 수정을 마치면 "이 코드를 PR 리뷰한다면 뭘 지적할까?" 관점으로 자기 코드를 리뷰합니다. 불필요한 변경, 네이밍, 중복을 한 번 더 점검합니다.

**4. 그룹 단위 처리**

75개를 한번에 처리하면 충돌과 사이드 이펙트가 폭발합니다. 성격별로 6그룹으로 분류했습니다:

| 그룹 | 내용 | 이슈 수 |
|------|------|---------|
| 잔재/설정 정리 | pyproject, fly.toml, Pydantic v2 | 6 |
| FE 버그 | PUT→PATCH, toast 혼용 등 | 6 |
| BE 보안 | CORS, 시크릿, HTML 인젝션 | 5 |
| BE 버그 | 정기거래 중복, 레거시 데이터 | 5 |
| 코드 품질 | 봇 코드 중복, 환율 이중화 | 6 |
| 테스트 추가 | 커버리지 갭 | 8 |

각 그룹은 독립 워크트리에서 독립 에이전트가 처리합니다. 한 그룹이 끝나면 PR → CI 통과 → 머지 → 다음 그룹. 실패하면 해당 그룹만 수정합니다.

## 🤖 프롬프트 설계: 페르소나 + 실행 템플릿

에이전트에게 "이슈 고쳐"라고 하면 안 됩니다. 어떤 관점으로 코드를 봐야 하는지를 정의해야 합니다.

### 페르소나 (`.claude/rules/coding-persona.md`)

프로젝트에 체크인해서 모든 세션에서 자동 적용됩니다:

- **Claude Code가 읽기 좋은 코드**를 짠다 — 함수명만 보고 역할을 알 수 있어야 하고, 한 파일 안에서 흐름이 완결되어야 한다
- 주석은 "왜"를 설명하고, 코드 자체가 "무엇"을 설명한다
- 암묵적 규칙보다 명시적 코드를 선호한다

"읽기 좋은 코드"의 기준이 사람이 아니라 LLM이라는 점이 핵심입니다. LLM이 5개 파일을 넘나들어야 이해하는 구조는 나쁜 구조입니다.

### 실행 프롬프트 (`docs/prompts/code-review-execution.md`)

재사용 가능한 템플릿입니다. 페르소나, 작업 철학, 테스트 환경, GitHub 프로젝트 상태 업데이트 방법, 그룹 목록까지 한 파일에 담겨 있습니다. 다른 세션에서 `--dangerously-skip-permissions` 모드로 이 프롬프트를 넣으면 자율적으로 작업합니다.

## ⚙️ DevOps 자동화: 8종 워크플로우

코드리뷰를 처리한 후, 앞으로도 코드 품질이 유지되도록 자동화를 구축했습니다.

### PR마다 자동 실행

| 체크 | 하는 일 |
|------|---------|
| **커버리지 리포트** | BE/FE 커버리지 % PR 코멘트 |
| **pyright 타입 체크** | None 접근 등 타입 버그 감지 |
| **번들 크기 추적** | FE 빌드 후 gzipped 크기 코멘트 |
| **API 스키마 drift** | 엔드포인트/스키마 수 변화 감지 |
| **시크릿 스캔** | detect-secrets로 유출 차단 |

### 배포 후 자동 검증

| 체크 | 하는 일 |
|------|---------|
| **스모크 테스트** | 배포 30초 후 `/health` + 주요 엔드포인트 체크 |
| **자동 롤백** | 프로덕션 스모크 실패 시 `flyctl releases rollback` |

### 주간/월간 자동 스캔

| 주기 | 체크 | 하는 일 |
|------|------|---------|
| 매주 금 | **Radon 복잡도** | 함수 복잡도 변화 감지 → 악화 시 이슈 생성 |
| 매주 금 | **브랜치 정리** | 머지 후 2주 지난 브랜치 자동 삭제 |
| 매주 금 | **Stale 이슈** | 60일 미활동 → stale 라벨, 90일 → 자동 close |
| 매월 1일 | **TODO 추적** | 3개월 이상 된 TODO/FIXME 이슈화 |
| 매월 1일 | **Dead code** | vulture(BE) + knip(FE) 미사용 코드 감지 |

추가로 **Renovate**로 의존성 자동 업데이트, 보안 패치는 자동 머지 설정했습니다.

모든 워크플로우 결과는 **텔레그램**으로 받습니다. CI 커버리지, CD 스모크 결과, 주간 품질 리포트까지 전부 핸드폰에서 확인할 수 있습니다.

## 💡 마무리: 에이전트 시대의 코드 운영

AI 에이전트에게 코드를 맡기는 건 사람에게 맡기는 것과 같습니다. 신뢰할 수 있으려면:

1. **명확한 기준**이 필요합니다 (페르소나, 코딩 원칙)
2. **검증 루프**가 필요합니다 (TDD → 코드리뷰 → CI)
3. **실패 시 복구**가 필요합니다 (스모크 테스트 → 자동 롤백)
4. **점진적 퇴화를 감지**해야 합니다 (Radon, Dead code, 번들 크기)

이 안전장치가 있으면 에이전트에게 `--dangerously-skip-permissions`를 주고 돌려도 괜찮습니다. 테스트가 깨지면 CI가 잡고, 배포가 잘못되면 스모크가 잡고, 코드가 썩으면 주간 스캔이 잡습니다.

에이전트 개발의 속도를 올리는 건 더 좋은 프롬프트가 아니라, **더 단단한 안전장치**였습니다.
